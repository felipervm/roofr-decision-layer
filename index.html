03 / HOW I APPROACH THE WORK

Show the reasoning.
Make it reproducible.

A useful analysis should survive a second look. The source code, data-generation rules, and checks are open for review.

Explore the repository ↗
01

Start with the product and the user.

Read Roofr's public product materials. Frame a narrow hypothesis that complements its existing dashboards and CRM automations.

02

Build a model we can inspect.

Generate 1,200 synthetic records in Python with seed 418. Define open stages, a 10-day inactivity rule, and explicit denominators.

03

Check the data before the story.

Validate unique IDs, stage totals, positive values, and loss-reason completeness. Keep assumptions visible.

04

Translate findings into a test.

Propose a pilot. Measure whether exceptions get resolved faster and whether the review creates unnecessary work.

04 / WHAT I'D TEST WITH THE TEAM

Four weeks. One focused hypothesis.

Can an exception-first review improve follow-through?

WEEK 01

Define the signal.

Agree on eligible stages and inactivity thresholds with product and support. Manually inspect false positives.

WEEK 02

Establish the baseline.

Measure unresolved exceptions and time to next action. Segment by stage and source.

WEEKS 03–04

Test the review.

Compare with baseline and, where feasible, a similar untreated group. Track completion, time to resolution, and review burden.

A proposed experiment, not a measured result. A before/after comparison alone would not establish causality.
